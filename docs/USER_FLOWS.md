# EuroID — Detailed User Flows

> Step-by-step flows covering authentication, connector setup, policy configuration, simulation, deployment, and post-deploy monitoring. Each flow documents the UI element, API call, backend logic, and expected result per step.

## Flow 1: Authentication

### 1.1 First-Time Setup (Registration)

Local sign-in (no `VITE_OIDC_AUTHORITY`): `backend/src/modules/auth/auth-local.service.ts`, `frontend/src/features/auth/LoginPage.tsx`.

| Step | User Action | UI Element | API Call | Backend Logic | Result |
|------|------------|------------|----------|---------------|--------|
| 1.1.1 | Opens `http://localhost:5173` | App loads; `LocalAuthProvider` checks the session (not on the single sign-on return `/auth/saml-callback`, whose code exchange decides the session: a 401 of that check could come after the exchange and clear the tokens it stored) | `GET /api/v1/auth/me` | No session cookie: 401 | Redirected to `/login` |
| 1.1.2 | — (auto) | LoginPage mounts | `GET /api/v1/auth/setup-status` | Counts `admin_users`: `{ hasAdminUsers: false }` | Form switches to **Create account** mode with "First account will be created as Super Admin" |
| 1.1.3 | Fills Full name, Email, Password and, only when the server sets `SETUP_TOKEN`, Setup token | Ant Design inputs. Password: at least 12 characters with an upper case letter, a lower case letter, a digit and a special character, the API's rule | — | — | Local form state updated |
| 1.1.4 | Clicks **Create account** | Button, loading spinner | `POST /api/v1/auth/register` `{ name, email, password, inviteToken? }` | Zod `STRONG_PASSWORD_SCHEMA`: 12 to 128 characters, upper case, lower case, digit and special character (else 400); the email is trimmed and lowercased. With no admin yet: a set `SETUP_TOKEN` must equal `inviteToken` (constant-time compare, else 403); without `SETUP_TOKEN` the setup is open only when `NODE_ENV` is `development` or `test`, and anywhere else answers 403 "Initial setup is disabled until SETUP_TOKEN is set on the server..." (`backend/src/modules/auth/first-admin-setup.ts`); the password is hashed with argon2id (19 MiB, 2 iterations, 1 lane) and kept as the first of the last 5 hashes (`passwordHistory`); one atomic upsert creates the only `super-admin`, in tenant `DEFAULT_TENANT_ID` (else `dev-tenant`), so a second first registration racing it gets 409. No session is issued | `201 { user: { id, email, name, role: 'super-admin', tenantId } }`. "Account created! Please sign in." and the form switches to Sign in (1.2) |

### 1.2 Subsequent Login (Success)

| Step | User Action | UI Element | API Call | Backend Logic | Result |
|------|------------|------------|----------|---------------|--------|
| 1.2.1 | Opens app | LoginPage mounts | `GET /api/v1/auth/setup-status` | Returns `{ hasAdminUsers: true }` | **Sign in** form: Email, Password, [Sign in], [Create an account] (needs an invite, Flow 18.3); [Sign in with SSO (SAML)] when SAML is configured |
| 1.2.2 | Enters email and password, clicks **Sign in** | Button, loading spinner | `POST /api/v1/auth/login` `{ email, password }` | Throttled per client IP in the shared security state store (`AUTH_THROTTLE_SHORT_LIMIT`, default 5 per second; `AUTH_THROTTLE_MEDIUM_LIMIT`, default 15 per minute; 503 while the store is down). Zod applies the registration password rule (400). Finds the active admin by email, refuses a single sign-on account, verifies the argon2id hash (a legacy bcrypt hash is verified, then replaced by argon2id). MFA on: `{ mfa_required, mfa_token }` (5 minutes) and the MFA step (`POST /api/v1/auth/mfa/challenge`). Tenant `mfaRequired` without MFA: `{ mfa_enrollment_required, mfa_enrollment_token }`, a 5-minute token that only sets up MFA. Otherwise a session: an access JWT (HS256, issuer `euroid-local`, `JWT_EXPIRY`, default 1 hour; claims `sub`, `email`, `name`, `roles`, `tenantId`, `tokenVersion`) and an opaque refresh token (48 random bytes, stored as its SHA-256, `REFRESH_TOKEN_EXPIRY_DAYS`, default 7); `lastLoginAt` is set | `201 { access_token, refresh_token, user }` plus httpOnly, SameSite strict cookies (Secure in production): `access_token` (path `/`, 15 minutes) and `refresh_token` (path `/api/v1/auth`, 7 days) |
| 1.2.3 | — (auto) | Tokens kept in memory only (`auth/token-store.ts`), never in localStorage; `euroid-login-success` event | — | — | Redirect to the page a signed-out visit asked for (a deep link to `/identities/<id>?tab=access` sends the visitor to `/login` and, after the sign-in, the MFA step included, back there; `auth/return-url-store.ts`, sessionStorage, same-origin paths only), else to `/`. **Sign in with SSO** sends that page to `GET /api/v1/auth/saml/login?returnUrl=`, the API carries it through the SAML RelayState, and `/auth/saml-callback` opens it after the sign-in. A reload checks the session with `GET /api/v1/auth/me` (cookie). On a 401 the client calls `POST /api/v1/auth/refresh`, which issues a new access token and a new refresh token (the old one stops working). `JwtAuthGuard` reads `isActive`, `tokenVersion` and the role from the database on every request, so a revocation, deactivation, password change or role change applies from the next request |
| 1.2.4 | (auto) When the tenant requires MFA and the admin has none: a password sign-in (1.2.2) or a single sign-on (`/auth/saml-callback`, `POST /api/v1/auth/saml/exchange`) answers `{ mfa_enrollment_required, message, mfa_enrollment_token, user }` | Account security `/settings/security?mfa_enrollment=true` on its own, without the menu and the top bar: "MFA Required" alert with [Sign out] and the setup wizard (Scan QR code, Verify code, Backup codes). Any other page, `/login` included, leads back here while the session is the enrollment token (`frontend/src/auth/MfaEnrollmentGate.tsx`) | `GET /api/v1/auth/mfa/status`, `POST /api/v1/auth/mfa/setup`, `POST /api/v1/auth/mfa/verify-setup` `{ code }`, each with the `mfa_enrollment_token` as Bearer. The setup is requested once per visit of the page: each request stores a new secret | The token (5 minutes, scope `mfa-enrollment`, no role) is kept in memory as the access token, with no refresh token and no cookies (`frontend/src/auth/mfa-enrollment.ts`). Only `GET /api/v1/auth/me`, `GET /api/v1/auth/mfa/status`, `POST /api/v1/auth/mfa/setup` and `POST /api/v1/auth/mfa/verify-setup` accept it (`MfaEnrollmentScopeGuard`, global); every other route answers 403 "This sign-in can only set up MFA...", `POST /api/v1/auth/change-password` included | [Done] after the backup codes signs the admin out: they sign in again with their password or through single sign-on, and now get the MFA step (Flow 1.2.2, `mfa_required`). [Sign out], a reload or 5 minutes without finishing also lead back to sign in |

### 1.5 Forgot Password

Local sign-in only: an account that signs in through single sign-on has no EuroID password. Code: `backend/src/modules/auth/password-reset.service.ts`, `frontend/src/features/auth/ResetPasswordPage.tsx`.

| Step | User Action | UI Element | API Call | Backend Logic | Result |
|------|------------|------------|----------|---------------|--------|
| 1.5.1 | Clicks **Forgot password?** | Link under the sign-in form | `GET /api/v1/auth/password-reset/config` | `{ byEmail, tokenTtlMinutes }`: `byEmail` is true when the deployment sets `SMTP_HOST` | With email: an Email field and [Send reset link]. Without: "This EuroID does not send email. Ask a super-admin of your organization for a password reset code" (Flow 18.9). Both offer [I have a reset code] (1.5.4) |
| 1.5.2 | Enters the address, clicks **Send reset link** | Button, loading spinner | `POST /api/v1/auth/password-reset/request` `{ email }` | Rate limited in the shared security state store: `PASSWORD_RESET_MAX_PER_IP` (default 10) per client IP and `PASSWORD_RESET_MAX_PER_EMAIL` (default 3) per address within `PASSWORD_RESET_WINDOW_MINUTES` (default 15), 429 above, 503 while the store is down. Then it answers. Only after the answer, and only for an active account that signs in with a password while email is on: a token of 32 random bytes, of which only the SHA-256 and the expiry are stored on the admin (a newer token replaces an earlier one), the mail, and `admin_user.password_reset_requested` (`adminUserId`, `mailSent`). An unknown address, a single sign-on or a deactivated account gets nothing | `202` with the same message for every address: "If an active admin account that signs in with a password uses this address, EuroID emails it a link to set a new password, valid for 30 minutes. No email? Ask a super-admin of your organization for a reset code." |
| 1.5.3 | Opens the link in the mail | Mail "Reset your EuroID password": `<FRONTEND_URL>/reset-password#token=<code>` | — | The mail is sent at once and not stored; a failed send is logged without the address or the token and not retried | Reset page "Set a new password". The token is read from the URL fragment (never sent to a server or in a Referer) and removed from the address bar |
| 1.5.4 | Enters the new password twice (with a super-admin's code: [I have a reset code], then the code), clicks **Set new password** | Reset page `/reset-password` (public) | `POST /api/v1/auth/password-reset/confirm` `{ token, newPassword }` | Rate limited per client IP like 1.5.2. Zod: a 64-character hex code and the registration password rule (400). The token must be the admin's current one and unexpired (`PASSWORD_RESET_TOKEN_TTL_MINUTES`, 15 to 60, default 30), of an active account that signs in with a password; otherwise 400 "This reset link or code is invalid, used or expired. Ask for a new one." A password among the last 5 is 400 and the token stays usable. Then the argon2id hash and `passwordHistory`, `tokenVersion` incremented, the refresh token and the reset token removed; MFA is not touched; `admin_user.password_reset_completed` (`adminUserId`) | "Password changed": every session of the admin ends and nobody is signed in. [Sign in] leads to 1.2, where MFA still applies. A password change (Account security) also voids an unused token |

## Flow 16: Outbound Webhooks

EuroID sends domain events to external systems (a SIEM, a ticketing system, your own service) as signed HTTPS POSTs. Admin > Webhooks (`/admin/webhooks`, super-admin, like every `/event-subscriptions` route). A delivery carries ids only (`buildWebhookBody`, `backend/src/modules/event-subscriptions/webhook-payload.ts`): `eventId`, `eventType`, `timestamp`, `aggregateId` and, when the event has them, `identityId`, `policyId`, `campaignId`, `driftId`, `anomalyId`; no names or email addresses: an id whose value holds an email address (an emitter that fell back to the email) is left out, `aggregateId` included. Headers: the subscription's custom headers, then `Content-Type: application/json`, `X-EuroID-Signature: sha256=<HMAC-SHA256 of the raw body with the signing secret>`, `X-EuroID-Event` and `X-EuroID-Delivery` (the delivery id, the same on every retry), which no custom header can replace. A delivery goes only to the subscription's URL: redirects are not followed (a 3xx answer is a failed delivery), the stored URL is checked again before each POST, and the host is resolved when the connection is made, every address checked by the SSRF guard: a host that resolves to a private, loopback, link-local, cloud metadata or reserved address is refused ("Refused to connect to <host>: ..."), also when it resolved to a public one when the subscription was saved. The answers carry the custom headers' names (`webhook.headerNames`) and `webhook.hasSigningSecret`, never the signing secret or a header value. The routes take the subscription's `_id`; another tenant's is 404.

## Flow 21: Audit Integrity

Checks that the audit log (`audit_events`) was not changed (backend `modules/audit`). Governance > Audit integrity (`/audit/integrity`, super-admin, like every route below; other roles do not see the entry). Each audit event written since the chain head stores its chain position `seq` (one chain per tenant, whatever process writes), `previousHash` (the `integrityHash` of the position before it) and `integrityHash`, the SHA-256 of `previousHash` and the canonical JSON of every stored field, payload included (`hashVersion: 2`). What the graph cannot show: accounts in the target systems, access assigned only in a target system (nothing writes it), and group nesting. Nesting is not modelled: no group-in-group membership reaches the graph (discovery reads groups without their members, the catalog has no parent group, and the member type a SCIM inbound group records is not read into it), so nothing writes `MEMBER_OF` and every path is one `HAS_ACCESS` step. An entitlement is one node, keyed by its native id, however the access came: a role-based rule's grant (in the resync, and in completed provisioning, which reports the rule's name for the target) and an SoD policy's entitlement are found as the entitlement catalog entry of the target on its system, by native id, else as the one entry with a native id that has that name (as Flow 25 names them). A group a rule names by display name therefore has its holders by rule and by request on the catalog's node. A target the catalog does not know, or names more than once, stays a node of its own under the rule's id (type that id in 24.2) until the catalog has it and a resync moves its holders. Between resyncs the graph follows events: completed provisioning (access added and removed), entitlement discovery (`discovery.completed`: the names, types and application of the system's catalog entries; entries the catalog dropped stay until the next resync) and deleted identities (`identity.deleted`, and an offboarding that deleted the Golden Record, remove the identity's node and access; an offboarding with a failed target keeps it, since that account still exists). Access granted while Neo4j was down is missing until the next resync. A role below super-admin is offered no resync and the page sends none.

## Flow 25: Access Intelligence

Reviewer quality, peer groups and their outliers, an identity's recommended entitlements and the unusual-request check (backend `modules/intelligence`). The nightly intelligence batch (Temporal schedule `intelligence-batch-daily`, `INTELLIGENCE_BATCH_CRON`, default `0 4 * * *` in UTC) builds the peer groups and scores each completed campaign once; no route computes them on demand and no page offers to. Peer groups hold the active identities (not soft-deleted, not `TERMINATED`) with a department or a job title, grouped by both; a group needs `INTELLIGENCE_PEER_GROUP_MIN_SIZE` members (default 3), and a build removes the groups it did not write (below the minimum size, or no identity has their department and job title any more). A member's access in a group is what they hold, as their identity page calls it Active: the groups, licenses and roles the role-based rules give them on a target system where their account is `SYNCED`, and the entitlements of their `ACTIVE` access requests; access found only in a target system does not count. An entitlement is named `system::nativeId`, as the request form's check names it: a rule-given one by its entitlement catalog entry (by native id, else by the one entry with a native id that has the rule's name for it), so a group held by rule and by request is one entitlement; a rule's target the catalog does not know, or names more than once, keeps its own name. Every view is advice: none grants, revokes or changes anything.

## Summary & Expected Outcomes

For test data numbers, expected database state after a full flow, and the complete data flow diagram, see [TEST_SCENARIO.md](TEST_SCENARIO.md).

The generic data flow pattern is:

```
[HR Source(s)] ──HR Feed──→ [EuroID Brain / Policy Engine] ──Provisioning──→ [Target System(s)]
                                     │
                          ┌──────────┼──────────┐
                          │ Person   │ Contract  │
                          │ profile  │ profiles  │
                          │ (name,   │ (per HR   │
                          │ email,   │ source:   │
                          │ status)  │ title,    │
                          │          │ dept,     │
                          │          │ manager)  │
                          └──────────┴──────────┘
```

Each HR source's record stays in the identity's `sources[]`, and reconcile merges them into one profile with mastery rules (the primary HR source drives contract-critical fields). For policy evaluation each HR source becomes a contract (title, department), derived from `sources[]` and not stored (`IdentityOnionService.buildProfileWithContractsForPolicy()`); a policy that matches the profile or any contract adds its operations. Targets receive the merged profile: there is no per-target contract binding.

Each policy evaluates user attributes against conditions and produces provisioning intents (group assignments, role assignments, license assignments). The deploy pipeline executes these intents through the connector layer.

## Sub-Flow A: Identity Correlation (Multi-Contract / Multi-Source)

> **Built.** The correlation rules are set in the Brain's "Identity Correlation" tab. For a concrete test case (HETU-based Finnish national ID correlation), see [TEST_SCENARIO.md](TEST_SCENARIO.md#hetu-correlation-test-case).

### Data Model: Sources and Policy Contracts

Each source's latest record stays in the identity's `sources[]` (`rawData`, `contractType`, `sourceRole`; one entry per source). Reconcile merges them into the one `profile`: the primary HR source alone writes contract-critical fields; for a field without a master its value wins and a secondary HR source fills gaps (`backend/src/modules/identity/reconciliation.service.ts`).

- **Person-level and employment fields** → `identity.profile`, merged with mastery rules
- **Contracts** → not stored: for policy evaluation `IdentityOnionService.buildProfileWithContractsForPolicy()` derives one contract per HR source (`id`, `title`, `department`, `isPrimary`, `status`) from `sources[]`, and `PolicyEngineService.evaluateWithPolicies()` evaluates each policy against the profile and against each contract, adding the operations of every match
- **Primary HR source** → `metadata.primaryHrSource`, chosen by contract type, connector contract tag, ingest priority, then the source priority order (`resolvePrimaryHrSource`)
- **Targets** → no per-target contract binding: every target gets the merged profile and the operations of every matching contract

### A.1 Matching

A record first matches by its source key (`sources.sourceName` + `sources.externalId`). Only when none matches do the correlation rules run, in order, first match wins (`IdentityCorrelationService.ensureIdentityFromUser()`, `backend/src/modules/identity/correlation/correlation-rule.engine.ts`). With no rule saved the only rule is `email`, so a person with different email addresses in two HR sources gets two identities.

### A.2 Brain Config: Identity Correlation Tab

| Setting | Options | Default | Purpose |
|---------|---------|---------|---------|
| **Correlation rules** (ordered) | `employeeNumber` (confidence 0.9), `email` (0.7), `hashedNationalId` with a source field such as `hetu` (0.95; only the hash is stored, the value is removed from the record, and Save refuses the rule while the server has no `CORRELATION_HMAC_SECRET`), `composite` over chosen fields (0.85), `heuristicName` (exact or fuzzy name match) | `email` | How an incoming record finds an existing identity |
| **Conflict action** | `auto-link`, `review` | `review` | With `review`, a match below 0.9 whose first and last names both differ goes to review |
| **Field Mastery** | An owner per field | The tenant's default mastery | Which source writes a field |
| **Attribute Writeback** | Target writeback, HR writeback | Target on, HR off | Write generated attributes (email, UPN) back to the Golden Record; push them to the HR system (needs an HR connector with write support) |

The settings are saved in the blueprint (`connectorConfigs['euroid-core'].correlationConfig`, read by `correlation-config.service.ts`). `confidenceThreshold` (default 0.7) has no field in the tab.

### A.3 Generic Correlation Flow

| Step | What Happens | Component |
|------|-------------|-----------|
| 1 | Admin adds a correlation rule (e.g. Hashed National ID, source field `hetu`) | Brain → "Identity Correlation" tab |
| 2 | Maps the correlation field in each HR source (e.g. `customAttributes.hetu`) | CSV HR `columnMap`, JSON API HR `fieldMap` |
| 3 | First source ingested | `IdentityService.saveOrUpdate()`: no source key or rule matches, so a new identity is created |
| 4 | Second source ingested with the same key | The rule finds the identity: the record is added to `sources[]`, event `identity.correlated` |
| 5 | Primary resolution | Reconcile picks the primary HR source and merges the profile |
| 6 | Policy evaluation | Each policy is evaluated against the profile and against each HR source's derived contract; the operations of every match are added |
| 7 | Provisioning | One account per target system (not one per source) |

### A.4 Edge Case: Conflict Detection

A match below `confidenceThreshold`, or a match below 0.9 whose first and last names both differ when the conflict action is `review`:

1. The matched identity is flagged (`metadata.correlationConflict`, `requiresReview`). The record gets an identity of its own, or waits on the conflict when a live identity has its email
2. Event `identity.correlation_conflict`
3. An operator resolves it: `POST /api/v1/identity/:id/resolve-conflict` with `merge`, `split` or `dismiss`

A national ID (0.95) or employee number (0.9) match is never sent to review for name differences.

Note: employment field differences across sources are **expected** (a person can be "Engineer" in Workday and "IT Consultant" in BambooHR).
